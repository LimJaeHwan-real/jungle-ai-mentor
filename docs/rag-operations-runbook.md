# RAG 운영 점검 절차

## 운영 화면과 접근

서버의 `ADMIN_EMAIL_ALLOWLIST`에 허용된 계정으로 로그인하면 `RAG 운영` 메뉴가 보인다. 목록이 비어 있으면 `/admin/*` 경로는 모두 거부된다. 허용 목록의 실제 이메일이나 인증값을 로그·문서에 적지 않는다.

운영 화면은 다음 읽기 전용 API를 사용한다.

- `GET /api/admin/rag/metrics`: 현재 서버 프로세스에서 기록한 검색 상태·경로별 후보·조회 실패·색인 결과·임베딩 요청과 일회성 웹 검색의 성공·실패 수, 최근 최대 200건의 검색·임베딩·웹 검색 지연 p95
- `GET /api/admin/rag/reindex-targets`: 현재 임베딩·분할 버전과 맞지 않거나 비활성인 문서 최대 100건
- `GET /api/admin/rag/reindex-jobs/:jobId`: 재색인 작업의 대상·성공·실패·중복 수와 항목별 안전한 오류 코드

지표는 메모리 집계이므로 서버 재시작 시 초기화되고 여러 서버의 합산값도 아니다. `재색인 대상`의 표시 건수 역시 최대 100건이며 전체 문서 수를 뜻하지 않는다. 이 화면은 자동 알림이나 재색인 실행을 수행하지 않는다.
검색 경로의 후보·선택 결과 수는 요청당 평균이 아닌 누적값이다. 결합·재정렬 실행 수는 두 검색 경로가 정상 완료된 요청만 세며, 경로별 조회 실패는 실패한 시도마다 센다. 임베딩 실패는 별도 임베딩 지표에 기록한다.
웹 검색의 `total`은 내부 근거 판정이 부족으로 끝난 뒤 검색 서비스가 호출된 횟수다. 최근 후기라는 이유만으로 판정과 병렬 호출하지 않는다. `used`는 채택할 인용 출처를 찾은 횟수, `noCitedSource`는 요청은 끝났으나 채택할 인용 출처가 없었던 횟수, `failed`는 API 키 누락·시간 초과·API/네트워크 오류 횟수다. 실패율은 `failed / total`이다. 지표에는 질문·검색 답변·출처 URL을 저장하지 않는다. 웹 검색 지연 p95는 전체 질문 응답 지연이 아니라 웹 검색 호출 시간만 나타낸다.

## 상태별 확인

| 상태·현상 | 확인과 대응 |
| --- | --- |
| `SEARCH_DEGRADED` 증가 | 임베딩 서비스와 PostgreSQL 검색 상태를 확인한다. 질의·비밀값은 로그에 남기지 않는다. 검색 장애를 블로그 수집으로 감추지 않는다. |
| `NO_ACTIVE_INDEX` 증가 | 활성 문서의 임베딩 모델·차원·모드·버전과 재색인 대상 목록을 확인한다. 운영에서 mock 색인을 답변 근거로 사용하지 않는다. |
| `INSUFFICIENT_EVIDENCE` 증가 | 질문 유형과 정답 자료 유무를 확인한다. 평가 질문의 라벨이 확정되기 전에는 점수 임계값을 임의로 바꾸지 않는다. |
| 색인 실패 증가 | 재색인 작업의 항목별 `errorCode`와 기존 활성 색인 유지 여부를 확인한다. `LEASE_RENEWAL_FAILED`는 작업 임대 연장을 확인하지 못했다는 뜻이므로 DB 연결과 동시 작업 상태를 점검한다. 원본 본문이나 제공자 오류 원문을 공개 로그에 복사하지 않는다. |
| 검색 p95 증가 | 최근 200건의 표본 수와 DB 쿼리 계획, 임베딩 API 지연을 함께 확인한다. 표본이 작거나 재시작 직후이면 장기 추세로 해석하지 않는다. |
| 벡터·키워드 조회 실패 증가 | 해당 검색 경로의 DB 오류와 쿼리 계획을 확인한다. 후보 수가 줄어든 것만으로 품질 개선·악화를 단정하지 않는다. |
| 임베딩 실패·재시도 증가 | 제공자·모델·모드·차원 설정과 외부 API 연결 상태를 확인한다. 지표에는 요청 횟수와 지연만 남기고 질문 본문·응답 벡터·API 키는 기록하지 않는다. |
| 웹 검색 실패율·p95 증가 | OpenAI API 연결·사용 가능 여부, 20초 제한, 최근 200건 표본 수를 확인한다. 자동 재시도는 없으며 외부 검색 실패를 내부 검색 장애로 집계하지 않는다. 질문·검색 결과·API 키를 지표나 공개 로그에 남기지 않는다. |

재색인 작업 등록은 `POST /api/admin/rag/reindex-jobs`로 최대 100개 대상을 영속 작업에 넣는 **쓰기 작업**이다. 운영 실행 전에는 대상 문서·모델·버전·기존 활성 색인과 복구 절차를 검토한다. 6-A 검증은 기존 로컬·운영 DB가 아닌 일회용 tmpfs PostgreSQL과 합성 문서에서만 작업을 등록했으며, 종료 후 컨테이너와 데이터를 삭제했다. 기존 로컬 DB와 운영 DB에는 재색인 작업을 등록하지 않았다.

## 품질 확인과 알림 경계

질문·정답 자료·충분성 라벨을 검토한 뒤 [평가 입력 안내](rag-retrieval-evaluation-input.md)에 따라 동일한 자료에서 기존 방식과 변경 후보를 비교한다. Recall@k, MRR, nDCG, 출처 정확도, 중복률, 충분성 precision/recall의 실제 측정값이 나오기 전에는 배포 차단 수치나 검색 임계값을 정하지 않는다.

자동 알림의 임계값·통지 대상·보존 기간은 아직 결정되지 않았다. 현재 운영 화면의 숫자와 상태는 관측 자료이며 알림이 발송되는 것으로 해석하면 안 된다. 프로세스 간 집계와 장기 보존이 필요하면 별도의 저장·관측 시스템 설계 및 승인이 필요하다.

2026-09-18 로컬 읽기 전용 확인에서는 재색인 작업·항목이 모두 0건이고, 활성 게시글 색인 40건과 과거 외부 블로그 색인 24건이 남아 있었다. 이 수치는 운영 DB의 재색인 상태가 아니다. 검증 당시 앱 프로세스가 없어 현재 프로세스 웹 검색 실패율·지연 p95를 읽을 수 없었고, 이전 실제 웹 검색 표본 1건의 약 14.8초 지연만 확인돼 분포나 오류율을 판정할 수 없다. 별도 검증 환경·허용된 외부 호출 범위·알림 및 보존 정책을 정하기 전에는 운영 재색인, 실제 웹 부하 시험, 장기 지표 저장·자동 알림을 적용하지 않는다.

2026-09-19 6-A 격리 검증에서는 정상 재색인, embedding 실패 시 기존 활성 chunk 보존과 안전한 오류 코드, 중복 작업 억제, 만료 임대의 재시작 복구를 실제 PostgreSQL 작업 큐로 확인했다. 검증 harness는 외부 `fetch`를 차단했고 호출 수는 0이었다. 이 결과는 재색인 상태 관리의 로컬 통합 증거이며 실제 OpenAI embedding, 대량 자료, 운영 부하를 검증한 것은 아니다. 현재 프로세스 웹 검색 지연·오류율은 승인된 3건 표본을 실행하기 전까지 미검증으로 둔다.
