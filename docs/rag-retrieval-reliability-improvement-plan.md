## 1. 목적과 범위

이 문서는 정글 AI 멘토의 RAG(Retrieval-Augmented Generation) 검색 결과를 실제 운영에서 신뢰할 수 있게 만드는 개선 계획이다. 목표는 단순히 검색 결과를 늘리는 것이 아니라, **실제 임베딩으로 생성된 검증 가능한 근거만 답변에 사용하고**, 근거가 부족할 때는 이를 명확히 알리는 것이다.

범위는 문서 수집·색인, 임베딩 생성, 하이브리드 검색, 재정렬, 답변 근거 표시, 품질 평가와 운영 관측성이다. LLM의 문체 개선, GitHub MCP 분석 자체의 고도화, 무제한 웹 크롤링은 본 계획의 직접 범위가 아니다.

## 2. 현행 방식

### 2.1 색인

- 관리자 문서, 게시글, 블로그 수집 문서를 `documents`와 `document_chunks`에 저장한다.
- 문서는 최대 700자 단위로 분할하고, 앞선 chunk의 최대 120자를 겹친다.
- `sourceUrl`과 콘텐츠 SHA-256 해시를 이용해 같은 문서는 건너뛰고, 내용이 바뀌면 기존 chunk를 삭제한 뒤 다시 색인한다.
- chunk마다 1,536차원 embedding과 추정 token 수를 저장한다.

### 2.2 임베딩

- 기본 모델은 `text-embedding-3-small`이다.
- `OPENAI_API_KEY`가 없거나 OpenAI Embeddings 요청이 실패·예외·빈 결과를 반환하면, 현재는 토큰 해시 기반의 deterministic mock embedding으로 자동 전환한다.
- 색인과 질의 embedding 모두 같은 자동 전환 규칙을 사용한다.

### 2.3 검색과 답변

- 질의 embedding을 만들고 pgvector cosine distance(`<=>`)로 상위 chunk를 조회하며, 점수는 `1 - distance`로 계산한다.
- 벡터 질의가 성공해도 `BOARD_POST` 범주의 lexical 검색 결과를 합친 뒤, 하나의 `score` 값으로 정렬한다.
- 벡터 질의가 실패하면 최근 150개 chunk를 대상으로 단순 토큰 포함 비율을 계산하는 lexical 검색만 수행한다.
- 정글 지식 질문의 상위 점수가 0.05 미만이거나 결과가 없으면, 선택값에 따라 실시간 블로그 검색·가져오기 후 재검색한다.
- 결과의 제목, 본문, 범주, 출처 URL을 LLM 컨텍스트로 전달하고, 응답 API의 `references`에 검색 결과를 포함한다.

## 3. 현행 방식의 한계와 위험

### 3.1 운영 환경의 mock 자동 전환

현재는 API 키 누락, 인증·네트워크·한도 오류, 응답 형식 오류를 모두 mock embedding으로 흡수한다. 이 방식은 서비스가 계속 응답하는 장점이 있지만, 운영 데이터에 의미적 품질을 보장하지 못하는 벡터가 저장되거나 실제 vector와 mock vector가 섞일 수 있다. 이후 실제 API가 회복되어도 두 벡터 공간은 비교 가능하지 않아 검색 점수와 순위의 의미가 깨진다.

### 3.2 색인 원자성과 재색인 안전성

변경 문서는 기존 chunk를 먼저 삭제한 뒤 새 embedding을 저장한다. 새 임베딩 생성 중 일부가 실패하면 문서가 부분 색인 상태가 될 수 있으며, embedding 모델·차원·생성 시각·생성 모드를 기록하지 않아 재색인 대상을 신뢰성 있게 판단하기 어렵다.

### 3.3 검색 점수의 비교 불가능성

벡터 cosine similarity와 lexical 토큰 포함 비율은 서로 다른 척도다. 두 점수를 그대로 비교·정렬하면 우연한 단어 일치가 의미적으로 더 관련성 높은 문서를 앞설 수 있다. 또한 `BOARD_POST`만 lexical 병합 대상으로 고정되어 있어 다른 문서 범주에는 일관된 하이브리드 검색이 적용되지 않는다.

### 3.4 lexical fallback의 품질과 성능

fallback은 최근 150개 chunk를 메모리에서 순회해 공백 토큰 포함 여부만 확인한다. 한국어 조사·복합어·동의어를 처리하지 못하고, 데이터 증가에 따라 성능과 결과 재현성이 저하된다. 벡터 DB 오류와 "관련 문서 없음"도 같은 fallback 흐름에 섞여 원인 구분이 어렵다.

### 3.5 chunk와 근거의 품질

문자 수 기반 분할은 표, 제목, 코드, 목록, Markdown 구조를 보존하지 못할 수 있다. 답변에 출처 정보는 전달되지만, 인용한 문장 범위·chunk 식별자·검색 방식·점수·embedding 상태가 사용자와 운영자에게 충분히 드러나지 않는다.

### 3.6 fallback 임계값의 근거 부족

실시간 블로그 검색 여부는 상위 점수 0.05라는 고정값에 의존한다. 실제·mock embedding, 콘텐츠 유형, 언어, 모델이 바뀌면 이 값의 의미도 바뀐다. 품질 측정 세트와 목표 지표가 없어 임계값을 조정할 근거가 없다.

## 4. 확정 정책

### 4.1 환경별 임베딩 정책

| 환경 | 실제 임베딩 미사용 시 동작 | mock embedding 허용 여부 |
| --- | --- | --- |
| 운영(production) | 색인 작업은 실패로 기록하고 기존 정상 색인은 유지한다. 질의는 신뢰할 수 있는 답변을 생성하지 않고 일시적 장애 안내를 반환한다. | 금지 |
| 스테이징(staging) | 기본값은 운영과 동일하게 실패 처리한다. 검증 목적의 데모 환경으로 명시된 경우에만 별도 설정으로 허용한다. | 기본 금지 |
| 데모(demo) | `RAG_EMBEDDING_MODE=mock`처럼 명시적으로 선택한 경우에만 사용한다. 응답과 운영 화면에 mock 사용 사실을 표시한다. | 허용 |
| 개발(local) | 개발자가 명시적으로 선택한 경우에만 사용한다. 기본값과 설정 방법을 문서화한다. | 허용 |

운영 환경에서는 **API 키 누락, 원격 API 오류, 시간 초과, 빈 응답을 mock embedding으로 자동 전환하지 않는다.** 이 정책은 색인과 질의 모두에 적용한다. mock과 실제 embedding을 같은 데이터베이스·같은 검색 인덱스에 혼합하지 않는다.

### 4.2 신뢰할 수 없는 검색 결과 처리

- 실제 embedding의 모델·차원·버전이 질의와 호환되지 않으면 해당 chunk를 검색 후보에서 제외한다.
- 임계값 미달, 근거 부족, 검색 장애는 서로 다른 상태 코드와 사용자 메시지로 구분한다.
- 근거 부족일 때 LLM이 지식을 보완해 단정하지 않도록, "등록된 근거에서 확인하지 못했다"는 응답 경로를 둔다.
- 실시간 외부 검색은 사용자 설정 및 별도 출처 정책에 따르며, RAG 검색 장애를 숨기기 위한 자동 대체 수단으로 사용하지 않는다.

## 5. 목표 상태

```text
문서 수집
  → 정제 및 구조 보존 chunking
  → 실제 embedding 생성·검증
  → 메타데이터와 함께 원자적으로 색인

사용자 질의
  → 실제 query embedding 생성·검증
  → vector 후보 + 전문 검색 후보
  → 점수 정규화·중복 제거·재정렬
  → 신뢰도 판정
  → 근거가 충분할 때만 인용 가능한 답변 생성
  → 출처·chunk·점수·검색 상태 반환
```

목표 상태의 핵심은 다음과 같다.

- 실제 임베딩 기반 색인과 질의의 모델 호환성이 보장된다.
- 벡터·키워드 검색은 일관된 후보 생성 단계로 동작하고, 통합 점수는 명시적으로 계산된다.
- 검색 결과에는 provenance(문서·chunk·출처·색인 버전)가 있고, 답변은 제공한 근거에 연결된다.
- 운영자는 품질 저하·색인 실패·검색 장애·모델 불일치를 관측하고 재처리할 수 있다.

## 6. 개선 계획

### 6.1 임베딩 실행 모드와 실패 처리

1. `RAG_EMBEDDING_MODE`를 `real`, `mock`으로 분리하고, 실행 환경별 허용 조합을 검증한다.
2. production에서는 `real`만 허용하고, 시작 시 API 키 존재와 모델 설정을 검증한다. 값 자체는 로그에 남기지 않는다.
3. OpenAI 요청 실패는 원인을 분류해 재시도 가능한 오류와 즉시 실패 오류로 나눈다. 제한된 횟수의 exponential backoff와 timeout을 적용한다.
4. embedding 응답의 차원과 유한 숫자 여부를 검증한다. 기대 차원과 다르면 색인·질의를 실패 처리한다.
5. embedding 생성 결과에 `provider`, `model`, `dimension`, `mode`, `generatedAt`을 부여한다. mock일 때는 반드시 `mode=mock`으로 기록한다.
6. 기존 mock 벡터는 운영 검색에서 제외하고, 실제 embedding으로 재색인할 수 있는 목록을 제공한다.

### 6.2 색인 모델과 원자성

1. 문서와 chunk에 `embeddingModel`, `embeddingDimension`, `embeddingMode`, `embeddingVersion`, `indexedAt`, `indexStatus`, `indexErrorCode`를 저장한다.
2. 변경 문서는 새 chunk·embedding을 임시 상태로 모두 생성·검증한 뒤 하나의 트랜잭션에서 활성 버전을 교체한다.
3. 실패한 색인은 기존 활성 버전을 삭제하지 않고 `FAILED` 상태와 안전한 오류 분류만 남긴다.
4. 모델 또는 chunking 규칙이 바뀌면 콘텐츠 해시만이 아니라 index version을 기준으로 재색인한다.
5. 관리자용 재색인 작업은 대상 수, 성공·실패 수, 실패 원인, 실행 버전을 반환한다.

### 6.3 구조 보존 chunking

1. Markdown 제목, 문단, 목록, 코드 블록, 표를 우선 경계로 사용한다.
2. 각 chunk에 문서 제목, 섹션 경로, 원문 범위, 순서, source URL을 메타데이터로 저장한다.
3. chunk 크기는 문자 수가 아닌 토큰 기준으로 측정하고, 문서 유형별 기본값은 평가 세트로 조정한다.
4. overlap은 임의 문자 겹침보다 인접 문장 또는 섹션 문맥을 보존하는 방식으로 바꾼다.
5. 너무 짧은 chunk, 중복 chunk, 추출 실패 문서를 색인 전 검출한다.

### 6.4 하이브리드 후보 검색과 재정렬

1. pgvector 검색은 실제 embedding·동일 모델·동일 차원·활성 색인 조건으로 후보를 가져온다.
2. 키워드 검색은 PostgreSQL 전문 검색 또는 한국어 처리에 적합한 검색 구성으로 전환한다. 최근 150개만 순회하는 방식은 제거한다.
3. 모든 문서 범주에 같은 후보 생성 정책을 적용하되, 질문 유형과 권한에 따른 범주 필터는 명시적으로 둔다.
4. vector와 lexical 결과는 각 후보군 안에서 정규화한 뒤, 가중 결합 또는 RRF(Reciprocal Rank Fusion)로 합친다. 서로 다른 원점의 점수를 직접 비교하지 않는다.
5. 동일 문서의 인접·중복 chunk를 줄이고, 문서 다양성을 보장한 상위 후보를 reranker에 전달한다.
6. 2단계 reranker를 도입한다. 초기에는 규칙 기반 또는 경량 모델로 정확성·비용을 확인하고, 평가 결과가 뒷받침될 때만 외부 reranking 모델을 채택한다.

### 6.5 신뢰도 판정과 답변 근거

1. top-1 점수 하나 대신 top-k 점수 분포, 질의-문서 일치, 출처 신뢰도, reranker 점수, 모델 호환성을 함께 사용한다.
2. "근거 충분", "근거 부족", "검색 장애", "색인 없음", "외부 보강 결과" 상태를 응답에 분리한다.
3. 답변의 각 핵심 주장에 문서 제목, URL, section/chunk 식별자, 짧은 인용 범위를 연결한다.
4. LLM에는 선택된 근거만 전달하고, 근거 밖의 내용을 사실처럼 단정하지 않도록 답변 계약을 강화한다.
5. 사용자 화면에는 최소한 출처 제목·URL·관련 발췌·검색 상태를 표시하고, 운영 화면에는 점수와 검색 경로를 추가로 표시한다.

### 6.6 블로그 검색 fallback 재정의

1. 벡터 DB 오류나 임베딩 장애는 블로그 자동 수집으로 감추지 않고 장애로 기록·응답한다.
2. "근거 부족" 상태에서만, 사용자가 허용한 경우에 한해 외부 검색 보강을 수행한다.
3. 외부에서 수집한 문서는 출처, 수집 시각, 라이선스·이용 조건 확인 상태, 추출 성공 여부를 저장한다.
4. 실시간 보강 결과는 기존 지식 베이스 결과와 구분해 표시하고, 답변에 사용하기 전 동일한 색인·품질 검사를 거친다.
5. 고정 점수 `0.05`는 평가 세트에서 결정한 환경별 임계값 또는 신뢰도 모델로 대체한다.

## 7. 단계별 실행과 완료 기준

| 단계 | 주요 작업 | 완료 기준 |
| --- | --- | --- |
| 1. 정책과 설정 | 실행 환경 판별, `RAG_EMBEDDING_MODE`, production 차단 규칙, 오류 코드 정의 | production에서 mock 설정·자동 fallback이 시작 단계에서 거부되고, demo의 명시적 mock만 동작한다. |
| 2. 색인 안전성 | embedding 메타데이터, 버전, 트랜잭션 기반 교체, 재색인 큐 | 실패 색인이 기존 활성 색인을 훼손하지 않고, mock·구버전 대상만 재색인할 수 있다. |
| 3. chunk 품질 | 구조 보존 분할과 provenance 저장 | 샘플 문서에서 섹션 경계·원문 범위·중복률 기준을 충족한다. |
| 4. 검색 품질 | 전문 검색, 후보 결합, 다양화, reranking | 평가 세트에서 기존 방식보다 Recall@k·MRR·근거 정확도가 개선된다. |
| 5. 답변 신뢰성 | 신뢰도 상태, 인용 연결, 근거 부족 응답 | 모든 RAG 답변이 근거 또는 명시적 근거 부족 상태를 갖는다. |
| 6. 운영 준비 | 지표, 대시보드, 알림, 운영 절차 | 장애·재색인·품질 하락이 관측되고 대응 절차가 문서화된다. |

각 단계는 기능 플래그 또는 버전 필드로 점진 적용한다. 대규모 기존 데이터 재색인은 새 검색 경로가 평가 기준을 통과한 뒤 배치 작업으로 수행하며, 완료 전에는 기존 활성 색인을 유지한다.

## 8. 검증 및 평가 계획

### 8.1 자동 테스트

- production에서 API 키 누락, API 오류, timeout, 빈 embedding 응답이 발생할 때 mock 벡터가 생성·저장되지 않는지 확인한다.
- demo에서 명시적 mock 모드만 동작하고, 응답·메타데이터에 mock 상태가 표시되는지 확인한다.
- 실제 embedding 응답의 차원 불일치·NaN·빈 배열을 거부하는지 확인한다.
- 색인 중 실패 시 기존 활성 chunk가 유지되는지, 성공 시에만 새 버전으로 교체되는지 확인한다.
- vector DB 장애, 전문 검색 장애, 근거 부족, 결과 없음의 응답 상태와 로그 코드가 서로 다른지 확인한다.
- 인용된 chunk가 실제 답변 컨텍스트에 포함되었고 해당 문서·출처와 연결되는지 확인한다.

### 8.2 오프라인 품질 평가

1. 정글 학습, 입학, 상담, 게시글, FAQ, 블로그 등 대표 질문과 정답 문서·chunk를 포함한 평가 세트를 만든다.
2. 각 질의에 대해 Recall@k, MRR, nDCG, 출처 정확도, 중복률, 근거 부족 판정의 precision/recall을 측정한다.
3. 현행 검색과 개선 검색을 같은 데이터·같은 평가 세트에서 비교한다.
4. 모델, chunk 크기, overlap, fusion 가중치, reranker, 임계값을 변경할 때마다 결과를 버전별로 저장한다.
5. 평가 세트에는 검색하면 안 되는 질문과 모호한 질문도 포함해, 그럴듯하지만 근거 없는 답변을 줄이는지 확인한다.

### 8.3 배포 전 검증 기준

- production 설정에서 mock embedding 코드 경로가 실행 불가능함을 통합 테스트로 보장한다.
- 활성 문서의 embedding 모델·차원·모드가 모두 호환되는지 점검한다.
- 정한 품질 기준을 충족하지 못하면 검색 알고리즘·임계값 변경을 배포하지 않는다.
- 부하 테스트로 색인 처리량, p95 검색 지연, 외부 API 오류율, DB 쿼리 계획을 확인한다.

## 9. 운영 관측성과 장애 대응

다음 항목은 비밀값 없이 구조화 로그·메트릭으로 남긴다.

- embedding 요청 수, 성공·실패·재시도 수, 지연 시간, provider/model/dimension/mode
- 문서 색인 수, 활성·실패·보류 상태, 재색인 대상 수와 실패 코드
- 검색 경로(vector, lexical, fusion, reranker), 후보 수, 최종 결과 수, 신뢰도 상태
- 근거 부족 응답률, 외부 검색 보강률, 사용자 피드백과 출처 클릭률
- vector DB·전문 검색·외부 embedding 서비스의 오류율과 p95 지연

알림은 production에서 mock embedding 시도가 감지되었을 때, embedding 실패율·검색 장애율이 임계값을 넘었을 때, 활성 색인의 모델 불일치가 발견되었을 때 발생시킨다. 장애 중에는 정상 색인 데이터만 검색하고, 신뢰할 수 있는 검색이 불가능하면 사용자에게 장애 사실과 재시도 안내를 제공한다.

## 10. 비목표와 결정 필요 사항

### 비목표

- 운영 장애를 숨기기 위한 mock 자동 전환
- 무제한 외부 웹 수집 또는 출처 검증 없는 자동 색인
- 근거가 없는 일반 지식을 RAG 답변으로 포장하는 동작
- 평가 없이 embedding 모델·reranker·임계값을 교체하는 동작

### 후속 결정 필요 사항

- production/staging/demo를 판별하는 배포 환경 변수와 배포 파이프라인 기준
- 사용할 embedding provider·모델·차원, 비용 상한, 재시도·timeout 정책
- PostgreSQL 전문 검색 구성과 한국어 형태소 처리 도입 여부
- reranker의 자체 호스팅·외부 API 사용 여부와 개인정보·비용 정책
- 평가 세트의 소유자, 정답 라벨링 절차, 배포 차단 임계값
- 외부 블로그 수집의 허용 도메인, 저작권·이용 약관, 보존·삭제 정책

이 결정들은 운영 정책과 데이터 경계를 바꿀 수 있으므로, 구현 전에 별도 승인과 기록이 필요하다.

## 11. 기능 단위 PR 및 병합 절차

각 단계는 독립적으로 검토·되돌리기·배포할 수 있는 기능 단위 PR로 진행한다. 한 PR에는 하나의 사용자·운영 가치와 그에 필요한 테스트·문서만 포함하며, 관련 없는 리팩터링과 환경 변경을 섞지 않는다.

| PR | 범위 | 병합 전 필수 확인 | 병합 후 조치 |
| --- | --- | --- | --- |
| 1. 임베딩 운영 정책 | 환경별 mock 차단, embedding 메타데이터, 안전한 색인 교체 | 단위 테스트, backend build, production mock 차단 검증, 기존 활성 색인 보존 검토 | mock·구버전 색인 재색인 대상 집계 |
| 2. 구조 보존 색인 | 섹션 기반 chunking, provenance, 색인 오류 코드 | chunk 경계·중복·원문 범위 테스트 | 신규 문서부터 적용하고 기존 문서 재색인 계획 확정 |
| 3. 하이브리드 검색 | 전문 검색, 후보 결합, 다양화 | 평가 세트의 Recall@k·MRR 비교, 쿼리 성능 확인 | 기능 플래그로 점진 활성화 |
| 4. 재정렬·신뢰도 | reranking, 근거 부족·장애 상태 | 정답·비정답·모호 질의 평가, 비용·지연 검토 | 임계값과 실패율 모니터링 |
| 5. 근거 UI·관측성 | 인용 표시, 검색·색인 집계와 읽기 전용 재색인 대상 조회 | API 계약·접근성·로그 비밀값 검사 | 대시보드와 장애 대응 절차 활성화 |

### 공통 흐름

1. 최신 `main`에서 `codex/rag-<기능>` 브랜치를 만든다.
2. 해당 기능의 코드·테스트·문서를 함께 커밋하고, 의도한 파일만 스테이징했는지 확인한다.
3. `main` 대상 PR을 생성한다. PR 본문에는 목적, 변경 사항, 검증 결과, 데이터 영향, 롤백 방법과 리뷰 포인트를 기록한다.
4. CI와 필수 검증이 통과하면 즉시 병합한다. 운영 정책, DB 스키마, 외부 제공자·비용 경계 변경은 PR 본문에 데이터 영향·롤백 방법을 기록하고, 검증 결과를 확인한 뒤 즉시 병합한다.
5. 병합 후 `main`의 원격 SHA와 배포·재색인 상태를 확인한다. 병합된 브랜치는 작업트리가 깨끗하고 사용 중인 프로세스가 없을 때만 정리한다.

각 기능 PR은 검증 결과가 통과하면 Ready 상태로 전환해 바로 병합하고, 병합된 `main`을 다음 기능 PR의 기준으로 사용한다. 검증 실패·충돌·보호 규칙 위반이 있을 때만 병합을 중단하고 원인을 해결한다.

### 11.1 현재 구현 범위와 운영 제약

- `/admin/rag/metrics`는 프로세스가 실행되는 동안 검색 신뢰도 상태·누적 지연 시간과 색인 성공·실패 수를 제공한다. 인증된 운영자만 조회할 수 있으며, 질의·문서 본문·비밀값은 기록하지 않는다.
- `/admin/rag/reindex-targets`는 현재 embedding 모델·모드·버전·차원과 호환되지 않거나 비활성 상태인 문서의 메타데이터만 반환한다. 이 조회는 재색인을 실행하거나 기존 문서를 수정하지 않는다.
- 후보 결합 뒤에는 동일 문서의 여러 chunk보다 서로 다른 문서의 상위 chunk를 먼저 선택한다. 서로 다른 문서 후보가 부족할 때만 같은 문서의 다음 chunk를 보충한다.
- 외부 reranking 제공자를 도입하기 전에는 제목·본문의 질의어 직접 일치율로 후보 순서를 보정하고, 결과에 `rerankScore`를 함께 반환한다. 이 점수의 가중치 변경과 외부 모델 전환은 평가 세트 결과를 확보한 뒤 진행한다.
- `SEARCH_DEGRADED` 상태에서는 lexical 후보가 있더라도 LLM 답변·외부 블로그 보강·GitHub 분석을 실행하지 않는다. 사용자에게 재시도 안내만 반환하고, 이 상태를 근거 부족과 구분해 표시한다.
- 현재 집계는 인메모리 방식이므로 프로세스 재시작 또는 다중 인스턴스 환경에서 누적값이 이어지지 않는다. 영속 메트릭, 대시보드, 임계값 알림과 실제 재색인 큐는 운영 준비 단계의 후속 작업으로 남긴다.
